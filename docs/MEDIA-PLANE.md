# سطح اجرا (Execution Plane) — سرور تلگرام محلی و Worker Node

> مکمل [`ARCHITECTURE.md`](./ARCHITECTURE.md) — بخش ۹ و ۱۹.
> این سند دقیقاً به سؤال «تلگرام انگار سرور شخصی می‌دهد، آن چطور است؟» جواب می‌دهد.

---

## ۱. پاسخ کوتاه

تلگرام **سرور به شما نمی‌دهد**؛ تلگرام **نرم‌افزارِ سرور را متن‌باز کرده** و شما آن را روی
ماشین خودتان اجرا می‌کنید: [`tdlib/telegram-bot-api`](https://github.com/tdlib/telegram-bot-api)
(همان کدی که api.telegram.org را می‌چرخاند). به آن **Local Bot API Server** می‌گویند.

برای این کار به دو چیز نیاز دارید:

1. یک ماشین (VPS یا سرور خودتان) با دیسک کافی.
2. `api_id` و `api_hash` از [my.telegram.org](https://my.telegram.org) —
   یعنی باید یک «Application» ثبت کنید. این اختیاری نیست؛ سرور محلی با این اعتبارنامه‌ها
   به شبکه‌ی تلگرام وصل می‌شود.

با پرچم `--local` (معادل `TELEGRAM_LOCAL=1` در ایمیج‌های داکر) این محدودیت‌ها برداشته می‌شود:

| قابلیت | Bot API ابری (`api.telegram.org`) | Bot API محلی با `--local` |
|---|---|---|
| دانلود فایل با `getFile` | **حداکثر ۲۰ MB** | **بدون سقف** (تا ۲GB عملاً) |
| آپلود فایل | ۵۰ MB (multipart) | **تا ۲۰۰۰ MB** |
| منبع فایل برای آپلود | فقط URL یا آپلود بدنه | **مسیر محلی دیسک یا `file://`** |
| خروجی `getFile` | یک `file_path` نسبی که باید با HTTPS دانلود شود | **مسیر مطلق روی دیسک سرور** (نیازی به دانلود نیست) |
| وبهوک | فقط HTTPS روی پورت‌های ۴۴۳/۸۰/۸۸/۸۴۴۳ | HTTP روی هر پورتی |
| نرخ ارسال پیام | ~۳۰ msg/s کلی، محدودیت‌های per-chat | **همان محدودیت‌ها باقی است** (این را برنمی‌دارد) |

آن چیزی که این معماری را متحول می‌کند سطر سوم و چهارم است:

> در حالت `--local`، متد `getFile` **مسیر مطلق فایل روی دیسک** را برمی‌گرداند.
> یعنی ffmpeg می‌تواند مستقیم آن مسیر را باز کند و **هیچ بایتی دانلود، آپلود یا کپی نشود.**

این دقیقاً همان چیزی است که «ادغام زیرنویس مثل MKVToolNix» را در این پروژه عملی می‌کند.

## ۲. سه توپولوژی — و آن‌که توصیه می‌کنم

### T1 — بدون سرور محلی (فاز ۰ تا ۳)
```
کاربر → تلگرام ابری → Worker → (فایل ≤۲۰MB) دانلود استریمی → R2 → (بعداً) نود
```
- ✅ ساده، بدون سرور، بدون هزینه‌ی اضافه.
- ❌ سقف ۲۰MB برای دانلود و ۵۰MB برای آپلود.
- کاربرد: زیرنویس خالص (که خودش کوچک است)، فایل‌های کوچک، و ساخت/تست تمام UI.

### T2 — همه‌چیز از سرور محلی (فاز ۴+) ← **توصیه‌شده**
```
                    ┌── وبهوک (forward) ──▶ Worker
تلگرام ◀──MTProto──▶ Local Bot API Server ─────┐
                    └── getFile → مسیر دیسک ──▶ ffmpeg (همان ماشین)
                                                  │
                            sendVideo(file://…) ◀─┘  (تا ۲GB، مستقیم از سرور محلی)
```
- ✅ فایل بزرگ، بدون عبور از Cloudflare، بدون هزینه‌ی ترافیک.
- ✅ یک «خانه‌ی file_id» واحد: هر `file_id` که Worker می‌بیند، روی همان سروری معتبر است که نود از آن دانلود می‌کند.
- ⚠️ ریسک تک‌نقطه‌ای: اگر VPS بخوابد، **دریافت update هم می‌خوابد** — راه‌حل در بخش ۷.

### T3 — ترکیبی (وبهوک ابری، فایل بزرگ غیرفعال)
```
تلگرام ابری → Worker   +   فایل‌های بزرگ: رد با پیام محترمانه یا مسیر Mini App/R2
```
- ✅ بدون ریسک تک‌نقطه‌ای.
- ❌ فیچر اصلی (ادغام ویدیوی بزرگ) کار نمی‌کند.

> **تصمیم پیشنهادی:** T1 را در فاز ۳ بسازید (تا UI و job ها کامل تست شوند)، و در فاز ۴ به T2
> مهاجرت کنید با «fallback» توصیف‌شده در بخش ۷. ستون `api_host` در جدول `jobs` و `artifacts`
> دقیقاً برای همین گذار گذاشته شده است.

## ۳. راه‌اندازی گام‌به‌گام (T2)

### گام ۱ — گرفتن اعتبارنامه
1. در [my.telegram.org](https://my.telegram.org) با شماره‌ی خودتان وارد شوید → `API development tools`
2. یک Application بسازید (نام دلخواه، مثلاً `shadow-node`) → `api_id` و `api_hash` را بردارید.
3. این‌ها راز هستند؛ در `.env` سرور نگه دارید، **هرگز در مخزن نگذارید**.

### گام ۲ — اجرای سرور با داکر

```yaml
# docker-compose.yml روی VPS
services:
  telegram-bot-api:
    image: aiogram/telegram-bot-api:latest      # یا هر ایمیجِ به‌روزِ دیگر
    restart: unless-stopped
    environment:
      TELEGRAM_API_ID:   ${TELEGRAM_API_ID}
      TELEGRAM_API_HASH: ${TELEGRAM_API_HASH}
      TELEGRAM_LOCAL:    "1"                     # ← کلید همه‌چیز
    volumes:
      - ./data/bot-api:/var/lib/telegram-bot-api # ← دیسک فایل‌ها؛ نود هم باید این را ببیند
    ports:
      - "127.0.0.1:8081:8081"                    # فقط روی لوکال‌هاست؛ هرگز روی اینترنت باز نکنید
  shadow-node:
    build: ./node
    restart: unless-stopped
    depends_on: [telegram-bot-api]
    environment:
      BOT_API_BASE:  http://telegram-bot-api:8081
      BOT_API_DIR:   /var/lib/telegram-bot-api    # همان volume، برای خواندن مستقیم فایل
      CONTROL_BASE:  https://shadow.<account>.workers.dev
      NODE_ID:       node-01
      NODE_SECRET:   ${NODE_SECRET}               # راز مشترک برای HMAC
    volumes:
      - ./data/bot-api:/var/lib/telegram-bot-api
      - ./work:/work                              # فضای کار ffmpeg
```
نکته‌ی حیاتی: **volume مشترک.** سرور بات فایل را در `--dir` می‌نویسد (`/var/lib/telegram-bot-api`)
و نود باید همان مسیر را ببیند تا `getFile` مسیرِ قابل‌استفاده بدهد.

### گام ۳ — اتصال وبهوک از طریق سرور محلی

از فاز ۴ به بعد، وبهوک را با سرور محلی ثبت کنید (نه با ابری):

```bash
# روی خود سرور؛ مسیر پشت reverse proxy قرار نگیرد
curl "http://127.0.0.1:8081/bot${TELEGRAM_TOKEN}/setWebhook" \
  -d "url=https://shadow.<account>.workers.dev/telegram" \
  -d "secret_token=${TELEGRAM_WEBHOOK_SECRET}" \
  -d "allowed_updates=[\"message\",\"edited_message\",\"callback_query\",\"channel_post\",\"edited_channel_post\",\"chat_join_request\",\"my_chat_member\",\"chat_member\"]"
```
- `allowed_updates` را محدود کنید: ترافیک کمتر، پردازش ارزان‌تر (و `chat_member` فقط اگر لازم دارید).
- `secret_token` همان مقدار امروز می‌ماند → مسیر اعتبارسنجی وبهوک در Worker **هیچ تغییری نمی‌خواهد**.

### گام ۴ — دسترسی Worker به نود

نود باید از اینترنت به Worker وصل شود (این سمت آسان است: خروجی HTTPS به workers.dev).
جهت مخالف (Worker → نود) لازم نیست، **مگر** بخواهید کار را push کنید؛ ما push نمی‌کنیم
(long-poll، بخش ۵). پس نود می‌تواند کاملاً پشت NAT بماند. خوبی این کار: سطح حمله صفر.

### گام ۵ — بررسی سلامت

```bash
# باید مسیر مطلق برگرداند، نه file_path نسبی
curl "http://127.0.0.1:8081/bot${TELEGRAM_TOKEN}/getFile" -d "file_id=<یک file_id واقعی>"
# → {"ok":true,"result":{"file_id":"…","file_size":123456789,"file_path":"/var/lib/telegram-bot-api/<token>/videos/file_1.mp4"}}
```
اگر `file_path` مطلق و روی دیسک نبود، `--local` فعال نیست. **این تنها معیار پذیرش این گام است.**

## ۴. معماری نود (shadow-node)

نود پروسه‌ی کوچکی است، نه یک سرویس بزرگ. مسیر پیشنهادی (Node.js + TypeScript):

```
shadow-node/
├── src/
│   ├── main.ts            # حلقه‌ی اصلی: heartbeat + long-poll claim + مدیریت ظرفیت
│   ├── control-client.ts  # کلاینت Worker: امضای HMAC، retry با backoff، تایم‌اوت
│   ├── executor.ts        # اجرای پروسه با timeout، سقف اندازه، محدودسازی، جمع‌آوری stderr
│   ├── handlers/
│   │   ├── media-mux.ts   # MuxPlan → argv → اجرا → probe خروجی → آپلود
│   │   └── chess-engine.ts# Stockfish با پروتکل UCI (اثبات چندکاره‌بودن نود)
│   ├── botapi.ts          # کلاینت Bot API محلی: getFile، sendVideo، sendDocument، editMessage
│   ├── progress.ts        # ترجمه‌ی خطوط پیشرفت ffmpeg → درصد + مرحله
│   └── cleanup.ts         # حذف فایل‌های موقت، حفظ سهمیه‌ی دیسک
└── Dockerfile             # ffmpeg + mkvtoolnix + stockfish + fonts (Vazirmatn برای هاردساب فارسی)
```

نکات اجرایی که تجربه‌ی میدانی نشان داده حیاتی‌اند:

| موضوع | قاعده |
|---|---|
| **ظرفیت** | نود اعلام می‌کند چند job همزمان می‌گیرد (مثلاً `slots = 2`). عنقصد کمتر از تعداد هسته بگذارید؛ ffmpeg خودش چندریسمانی است. |
| **تایم‌اوت** | حداکثر زمان هر job (مثلاً ۲ ساعت) + تایم‌اوت بی‌حرکتی stderr (مثلاً ۵ دقیقه) → جلوگیری از job زامبی. |
| **پیشرفت** | ffmpeg با `-progress pipe:1 -nostats` درصد درصد می‌دهد؛ mkvmerge با `--gui-mode` خطوط `#GUI#progress 42%`. بدون این، کاربر فکر می‌کند بات مرده. |
| **جداکردن خروجی** | `stdout` برای داده‌ی ماشینی (progress)، `stderr` برای لاگ؛ هر دو در `job_events` ثبت شوند اما با سقف (مثلاً ۲۰۰ خط آخر). |
| **دیسک** | قبل از شروع، `free space > 3 × size` را چک کنید؛ کمبود دیسک شایع‌ترین دلیل مرگ job است. |
| **پاکسازی** | فایل ورودی سرور بات را پس از پایان حذف کنید؛ فایل کاری خودتان را در `finally` حذف کنید. |
| **امنیت اجرا** | بدون `shell` (`spawn(cmd, argv)`)؛ نام فایل تولیدشده توسط خودمان (نه از ورودی کاربر)؛ `--` قبل از نام فایل. |
| **پایداری** | اگر کرش کرد، job های leased با انقضای lease برمی‌گردند؛ نود نباید حالت محلی حیاتی نگه دارد. |

## ۵. پروتکل داخلی (بین Worker و نود)

به‌جای طراحی از صفر، همان قرارداد بخش ۹ سند معماری:

| متد | مسیر | بدنه |
|---|---|---|
| `POST` | `/internal/v1/workers/heartbeat` | `{ nodeId, capabilities, slots:{total,busy}, version, hostMetrics }` |
| `POST` | `/internal/v1/jobs/claim` | `{ nodeId, capabilities, maxWaitMs: 30000 }` → `{ job \| null }` |
| `POST` | `/internal/v1/jobs/:id/progress` | `{ percent, stage, note }` (throttle در نود و در Worker هر دو) |
| `POST` | `/internal/v1/jobs/:id/complete` | `{ status, artifacts:[{kind, r2Key?, tgFileId?, apiHost, size}], metrics:{ms, cpuMs?}, error? }` |
| `POST` | `/internal/v1/jobs/:id/log` | `{ level, message, data }` (برای `job_events`) |

**امضا** (هر درخواست، از جمله heartbeat):

```
headers:
  X-Shadow-Node:  node-01
  X-Shadow-Ts:    1776000000              # ثانیه؛ پنجره‌ی ±۳۰۰s
  X-Shadow-Nonce: 8f3a…                   # یکتا؛ در DO کش می‌شود
  X-Shadow-Sig:   hex(HMAC-SHA256(NODE_SECRET, `${ts}.${nonce}.${sha256(body)}`))
```
- مقایسه‌ی امضا باید **time-constant** باشد (`crypto.subtle.verify` یا مقایسه‌ی بایت‌به‌بایت با OR تجمعی).
- اگر نود شما چند تایی شد، هر نود راز خودش را داشته باشد (و در D1 هش کنار `nodeId` نگه داری شود)
  تا بتوانید یکی را باطل کنید بدون دست‌زدن به بقیه.
- long-poll: درخواست claim تا ۳۰ ثانیه باز بماند؛ اگر job آمد، فوراً برمی‌گردد. این
  «تأخیر ~صفر» را با «بدون نیاز به سرور عمومی روی نود» جمع می‌کند.

## ۶. نمونه‌ی اجرا (چیزی که نود واقعاً اجرا می‌کند)

این دستورها را هسته‌ی خالص تولید می‌کند (`renderArgv`)؛ نود فقط اجرا می‌کند.

**الف) زیرنویس نرم در MKV (بدون کدگذاری مجدد — سریع و بی‌اتلاف):**
```bash
mkvmerge -o /work/out.mkv \
  --language 0:fas --track-name 0:فارسی --default-track-flag 0:1 \
  /work/subs.srt \
  /work/input.mp4
```
(در MKVToolNix قدیمی‌تر، `--default-track 0:1` — نود باید نسخه را چک کند و پرچم درست را بدهد.)

**ب) همان کار با ffmpeg (تک‌ابزار، ساده‌تر برای نگهداری):**
```bash
ffmpeg -nostdin -y -i /work/input.mp4 -i /work/subs.srt \
  -map 0 -map 1 -c copy -c:s srt \
  -metadata:s:s:0 language=fas \
  -disposition:s:0 default \
  -progress pipe:1 -nostats \
  /work/out.mkv
```

**ج) هاردساب فارسی در MP4 (کاربر در پلیر تلگرام می‌بیند):**
```bash
ffmpeg -nostdin -y -i /work/input.mp4 \
  -vf "subtitles=/work/subs.srt:force_style='FontName=Vazirmatn,FontSize=22,Outline=1'" \
  -c:v libx264 -crf 20 -preset veryfast -pix_fmt yuv420p \
  -c:a copy -movflags +faststart \
  -progress pipe:1 -nostats \
  /work/out.mp4
```
- `+faststart` برای استریم‌شدن در تلگرام لازم است.
- اگر GPU دارید: `-c:v h264_nvenc -preset p4 -cq 23` جای `libx264` (چند برابر سریع‌تر).
- فونت فارسی **باید** در ایمیج نصب باشد، وگرنه متن فارسی هاردساب به مربع تبدیل می‌شود.

**د) تحویل به کاربر (مستقیم از سرور محلی):**
```bash
curl "http://127.0.0.1:8081/bot${TELEGRAM_TOKEN}/sendVideo" \
  -F chat_id=123 -F supports_streaming=true \
  -F video="file:///work/out.mp4"  -F caption="✅ زیرنویس فارسی اضافه شد"
```

> ⚠️ نکته‌ی UX که نباید غافلگیرتان کند: کلاینت‌های تلگرام عموماً **زیرنویس نرم را نمایش نمی‌دهند**.
> پس «MKV با زیرنویس نرم» یک محصول آرشیوی است (VLC/Kodi/Plex)، و برای دیدن در تلگرام
> هاردساب لازم است. هسته‌ی `planMux` این را به‌صورت `warning` به کاربر می‌گوید — قبل از آنکه
> ده دقیقه منتظر بماند و بعد بفهمد.

## ۷. ریسک‌ها و پادزهرها

| ریسک | چرا مهم است | پادزهر |
|---|---|---|
| **تک‌نقطه‌ی خرابی** | در T2، خوابیدن VPS = خوابیدن کل بات (وبهوک هم از آنجا می‌آید) | (۱) نود heartbeat بفرستد؛ اگر >۳ دقیقه قطع بود، یک کرون `setWebhook` را موقتاً روی **ابر** بگذارد و فایل‌های بزرگ با پیام محترمانه رد شوند؛ (۲) در T2 فقط کارهای سنگین وابسته به نود شوند و مسیر متنی/پنل همیشه کار کند؛ (۳) سرور با restart خودکار و healthcheck داکر |
| **`file_id` بین دو سرور** | هر سرور Bot API `file_id` خودش را صادر می‌کند و تضمینی نیست روی دیگری معتبر باشد | ستون `api_host` روی `jobs`/`artifacts`؛ هر job فقط با سروری کار کند که فایل را از آن گرفته؛ در T2 یک میزبان واحد داشته باشید |
| **پهنای باند آپلود** | تلگرام فایل را از سرور شما می‌گیرد؛ آپلود ۲GB یعنی دقیقه‌ها اشغال پهنای باند | محدودیت `slots`، تایم‌اوت، و اگر ممکن است سرور با پهنای باند بالا/ترافیک نامحدود |
| **دیسک پر می‌شود** | سرور بات فایل‌ها را در `--dir` نگه می‌دارد | سقف حجم، پاکسازی دوره‌ای (کرون روی نود)، دیسک ≥ ۸۰GB و پایش فضای آزاد |
| **افشای سرور بات** | کسی که به سرور بات شما دسترسی داشته باشد، می‌تواند با توکن بات شما پیام بفرستد | سرور را **فقط** روی `127.0.0.1` بایند کنید و اگر لازم شد به بیرون، پشت Cloudflare Tunnel + Access/هدر راز دار؛ هرگز پورت ۸۰۸۱ را روی اینترنت باز نکنید |
| **شرایط استفاده‌ی تلگرام** | کاربردهای انبوه/اسپم‌مانند در سرور محلی مشکل‌ساز است | محدودیت نرخ per-chat را رعایت کنید (همان قواعد ابری)، و بار را با `--filter` روی چند سرور پخش نکنید مگر واقعاً لازم باشد |
| **نسخه‌ی نرم‌افزار** | پرچم‌های mkvmerge و رفتار ffmpeg در نسخه‌ها تغییر می‌کنند | `renderArgv` بر اساس `--version` خروجی‌گرفته از نود تصمیم بگیرد؛ pin کردن نسخه در `Dockerfile` |
| **هزینه‌ی VPS** | کوچک‌ترین منبع هزینه‌ی پروژه | یک VPS ۲vCPU/۴GB/۸۰GB برای شروع کافی است؛ GPU را فقط وقتی هاردساب زیاد شد |

## ۸. برآورد منابع

| بار کاری | منبع | تخمین |
|---|---|---|
| remux MKV (soft sub) | CPU تقریباً صفر، دیسک I/O | ۱۰۰MB → ۵–۲۰ ثانیه |
| هاردساب ۷۲۰p | CPU، بدون GPU | ۰.۳–۱× زمان ویدیو (۳۰دقیقه → ۱۰–۶۰ دقیقه) |
| هاردساب ۷۲۰p با NVENC | GPU | ۳–۸× سریع‌تر از libx264 |
| آپلود ۵۰۰MB به تلگرام | پهنای باند | ~۱–۵ دقیقه با ۲۰–۵۰ Mbps |
| سرور بات محلی | RAM | ~۱۵۰–۳۰۰MB + دیسک برای کش فایل |

حداقل ماشین پیشنهادی برای شروع: **۲ vCPU / ۴GB RAM / ۸۰GB SSD / ترافیک نامحدود**.
جایی که هزینه بالا می‌رود هاردساب است؛ برای آن یا GPU بگیرید یا صف را طولانی‌تر کنید
(و همین است که «job + پیشرفت + اعلان پایان» را ضروری می‌کند).
