# شطرنج در Shadow

> اجرا: `/chess` یا دکمه‌ی «♟ شطرنج» در منوی اصلی. کل فیچر روی Worker اجرا می‌شود
> و **هیچ نودی لازم ندارد** (برخلاف مدیا، بخش ۴ سند معماری).

| قابلیت | وضعیت | توضیح |

## ۲. ساختار کد

```
src/core/chess/          ← هسته‌ی خالص: هیچ import از تلگرام/Cloudflare/D1
├── types.ts             نمایش تخته (Int8Array(64))، Move، Position، GameStatus
├── board.ts             نام خانه، رنگ مهره، تشخیص حمله، کیش
├── fen.ts               parse/toFen + کلید وضعیت برای تکرار سه‌باره
├── movegen.ts           حرکات شبه‌قانونی، حرکات قانونی، صافی برای برداشت‌ها
├── make-move.ts         apply/undo در جا (بدون کپی تخته) + تبدیل UCI
├── san.ts               حرکت ↔ SAN، رفع ابهام، پسوند + و #
├── status.ts            مات، پات، ماده‌ی ناکافی، ۵۰ حرکت، سه‌بار تکرار
├── render.ts            تخته به‌صورت متن برای <pre> تلگرام
├── pgn.ts               ساخت PGN استاندارد
├── eval.ts              ارزیابی: ماده + PST + جفت فیل + مرحله‌ی بازی
├── engine.ts            negamax + alpha-beta + quiescence + iterative deepening
├── game.ts              GameRecord: فقط startFen + لیست SAN، بقیه با replay
├── perft.ts             ابزار تست (شمارش گره)
└── index.ts             نقطه‌ی ورود عمومی

src/telegram/db/chess.js        ← D1: chess_games (یک بازی فعال در هر چت)
src/telegram/ui/chessScreens.js ← متن و کیبورد (grammy)، بدون دسترسی به DB
src/telegram/features/chess.js  ← هندلرها + منطق «حرکت کاربر + پاسخ موتور»
```

قاعده‌ی وابستگی که رعایت شده: `features → ui → core` و `features → db → core`.
هیچ‌کدام از `core/*` به بیرون وابسته نیست؛ همین است که ۲۰۰+ تست آن بدون شبیه‌سازی
تلگرام اجرا می‌شوند.

## ۳. چرا تخته متن است، نه تصویر

- روی هر دستگاه و کلاینتی (وب، اندروید، iOS، دسکتاپ) بدون فونت اضافی درست دیده می‌شود.
- هیچ فایل/تصویر/WASM لازم نیست → باندل Worker سبک می‌ماند (سقف ۶۴MiB).
- کاربر می‌تواند بازی را کپی یا فوروارد کند.
- در تست، خروجی با snapshot مقایسه می‌شود.
- تخته عمداً با حروف لاتین (a-h، 1-8) رندر می‌شود تا در متن راست‌به‌چپ، ستون‌ها جابه‌جا نشوند.

اگر روزی تصویر خواستید، مسیر سازگار: SVG در `core` و تبدیل به PNG با `resvg-wasm` —
اما این کار باندل را سنگین می‌کند و برای شروع توجیه ندارد.

## ۴. الگوی callback (چرا حالت در سرور ذخیره نمی‌شود)

| داده | معنا |
|---|---|
| `cg:h` | خانه‌ی شطرنج |
| `cg:l:<level>` | بازی جدید؛ `0` = دو نفره، `1..4` = سطح موتور |
| `cg:resume` | ادامه‌ی بازی فعال |
| `cg:s:<sq>` | انتخاب مهره در خانه‌ی `sq` |
| `cg:m:<from>-<to>` | اجرای حرکت |
| `cg:pr:<from>-<to>-<type>` | اجرای حرکت با ترفیع |
| `cg:u` / `cg:r` / `cg:p` / `cg:stats` / `cg:x` | بازگشت / استعفا / PGN / آمار / لغو |

وقتی کاربر مهره‌ای را می‌زند، سرور همان پیام را با کیبورد جدید ویرایش می‌کند و
روی خانه‌های مقصد، `from` و `to` را **داخل خود callback** می‌گذارد. نتیجه:

- هیچ «انتخاب فعلی» در D1 یا حافظه‌ی ایزوله ذخیره نمی‌شود → با چند ایزوله و چند کاربر هم‌زمان درست کار می‌کند.
- حداکثر طول callback حدود ۱۵ بایت است (سقف تلگرام ۶۴ بایت).
- کلیک دوباره روی یک دکمه‌ی قدیمی، حرکت را دو بار اجرا نمی‌کند؛ چون نوشتن در D1
  به «FEN فعلی» مشروط است (optimistic concurrency) و درخواست دوم `stale` می‌گیرد.

## ۵. مدل داده

```sql
CREATE TABLE chess_games (
  id, chat_id, user_id,
  mode,        -- engine | local
  level, seed, -- سطح و دانه‌ی تصادفی برای بازتولیدپذیری پاسخ موتور
  start_fen,   -- وضعیت شروع
  fen,         -- کش وضعیت فعلی
  moves,       -- JSON array of SAN  ← منبع حقیقت
  status,      -- active | finished | abandoned
  result, reason, created_at, updated_at
);
```

تخته هرگز ذخیره نمی‌شود؛ از `start_fen` + `moves` بازپخش می‌شود. مزیت: یک منبع
حقیقت، امکان تشخیص تکرار سه‌باره، و سازگاری خودکار اگر منطق موتور تغییر کند.

`startGame` بازی فعال قبلی همان چت را `abandoned` می‌کند تا هیچ‌وقت دو تخته‌ی
فعال هم‌زمان نداشته باشیم.

## ۶. موتور: چه چیزی هست و چه چیزی نیست

- negamax با هرس آلفا-بتا، عمق‌افزا (iterative deepening) و **quiescence** روی برداشت‌ها.
- ارزیابی: ماده + جدول موقعیت (PST) + جفت فیل + PST شاه مرحله‌ای.
- بودجه **گره** به‌جای بودجه‌ی زمان → خروجی قطعی و قابل تکرار (لازم برای تست و «موتور vs موتور»).

| سطح | عمق | سقف گره | نویز | زمان معمول |
|---|---|---|---|---|
| آسان | ۱ | ۴هزار | ۱۵۰cp | ~۲ms |
| متوسط | ۲ | ۲۰هزار | ۵۰cp | ~۱۰ms |
| سخت | ۳ | ۶۰هزار | ۱۵cp | ~۳۰–۱۷۰ms |
| استاد | ۴ | ۱۵۰هزار | ۰ | ~۱۰۰–۳۰۰ms |

**صادقانه:** این موتور در حد «حریف قابل بازی» است، نه Stockfish. قدرت تقریبی
۱۲۰۰–۱۶۰۰. برای حریف قوی‌تر، Stockfish روی سطح اجرا (نود) اجرا می‌شود و از همان
پروتکل job استفاده می‌کند — نه اینکه موتور JS را پیچیده‌تر کنیم.

نکته‌ی بهینه‌سازی که در عمل تفاوت داشت: quiescence **باید fail-soft** باشد. با
fail-hard، همه‌ی حرکات ضعیف امتیازی برابر با آلفا می‌گیرند و لایه‌ی انتخاب سطح
(که «حرکات نزدیک به بهترین» را با نویز انتخاب می‌کند) حرکت‌های مضر را هم‌ارز بهترین
می‌دید؛ نتیجه: سطح «سخت» مهره می‌داد. این مورد الان تست رگرسیون دارد.

## ۸. کارهای بعدی (به ترتیب پیشنهادی)

1. **ساعت بازی**: `Durable Object` با `setAlarm` برای اتمام وقت (قدم ۲.۶ نقشه‌ی راه).
2. **بازی از FEN / پازل**: هسته آماده است (`newGame(fen)`)، فقط UI لازم دارد.
3. **موتور vs موتور با seed**: `simulation` — همان قدمی که قطعیت موتور را قفل می‌کند.
4. **نمودار/تصویر تخته** برای اشتراک‌گذاری (اختیاری).
5. **Stockfish روی نود** برای سطح «استاد واقعی».
